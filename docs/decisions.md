# Decisions
- React Native + Expo instead of Flutter (team familiarity).
- Development build, Android only; APK distributed via GitHub Releases.
- Own Kotlin ML Kit Expo module instead of a third-party wrapper.
- ID data stays on-device; automatic verification, no admin approval.
- Separate frontend/ and backend/ folders; shared logic in rentka-core/.
- Storage bucket in US-EAST1 (no-cost location); Firestore in Singapore.
- Matching: category is a hard filter; labels used only when both sides have usable non-generic labels; characteristic score is coverage of requested chips; min score 0.40, top 5, tiebreak trust then distance.
- Auto-fill: raw photoLabels and autofillSuggested are stored untouched next to the user-confirmed fields.
- Firebase CLI is a devDependency of backend/ (run with `npx firebase`), not a global install. backend/ config was written by hand to match `firebase init` output.
- Cloud Functions: TypeScript, Node 22, region asia-southeast1 (same as Firestore), maxInstances 2 to cap cost.
- Rules tests run in the emulator under the fake project id `demo-rentka`, so they cannot touch the real project and need no login.
- Synced core copies (frontend/src/core, backend/functions/src/core) are committed, so a fresh clone builds without running sync-core.bat.
- Sign-up fields live in one constant, `SIGNUP_FIELDS` in rentka-core/src/userProfile.ts; rules test R04d fails if it drifts from the `users` create rule.
- Roles are chosen at sign-up (Lender / Borrower / Both) and stored in `roles`; a role can be added later, never removed. The active side is a UI switch saved on the phone (expo-secure-store), limited to the roles the account holds. (Replaces "every account gets both roles".)
- Rules check the role when posting: lender role for items, borrower role for requests, plus the verified claim.
- Trust scores are per role (`lenderTrustScore`, `borrowerTrustScore` and their counts), written only by the rating function. A missing field means 3.00 / 0 (`verifyIdentity` no longer writes starting values, 2026-10-14).
- Verification has two outcomes only, verified or rejected. No "flagged", no manual approval. Lockout after more than 5 attempts in 24 hours lifts by itself.
- 2026-10-14: raw ID data never leaves the phone. The phone runs validateIdForm, the age check and the name match, and sends `verifyIdentity` only SHA-256("idType:normalized number") plus pass/fail results. The function stores HMAC-SHA256(`ID_HMAC_SECRET`, that hash) for the duplicate check (secret in Firebase Secret Manager, never in the repo). SHA-256 is plain TypeScript in rentka-core (`sha256.ts`), so no native crypto module and no rebuild. Trade-off: a modified app could fake the pass/fail results; App Check is the planned safeguard.
- ID step is one screen holding the fields in memory (form -> check -> result). It opens once right after sign-up and can be left; unverified users can enter the app but cannot post.
- `verifyIdentity` deployed 2026-10-10 with a 60-second code-load timeout (`FUNCTIONS_DISCOVERY_TIMEOUT=60`), because the default 10 seconds timed out on this machine. Artifact cleanup policy: images older than 1 day are deleted.
- Liveness check is planned, not built: on-device ML Kit Face Detection, pass/fail only, built with the ML Kit module after the lender, borrower and rental flows work. `LIVENESS_REQUIRED` in rentka-core is off until then. Limitation: it shows a live person is present, not that they own the ID. App Check (Play Integrity) for `verifyIdentity` is a trade-off to decide at that point.
- Tabs follow the prototype per role (Lender: Home, Listings, Requests, Messages; Borrower: Home, Requests, Messages); Profile is behind the header avatar.
- Login keeps Forgot Password; the "Login as" picker is dropped (role switching is from the header).
- 2026-10-14: Google sign-in is back ("Continue with Google" on Login and Register, then Complete your profile), via `@react-native-google-signin/google-signin` in the stage-2 native rebuild.
- 2026-10-14: email verification uses the free Firebase email link, required before the ID step and checked by `verifyIdentity` (`email_verified` in the login token). 6-digit code only if time allows.
- 2026-10-14: ID step order is ID type -> scan -> face check -> editable details (ID number, name, address, sex, birthdate) -> review -> result -> sign out to Login. Built in two stages: stage 1 without native code (manual entry), stage 2 one rebuild adding Google sign-in and the ML Kit module. Address and sex never leave the phone.
- 2026-10-14: dropdowns ("Sign up as", ID type, Sex) are a JS bottom-sheet `Select` component, no native package.
- A user who leaves the ID step or is rejected can still log in and use the app in limited mode (no posting, "Verify now").
- The Terms checkbox is asked once, at registration, not at every sign-in. The Terms and Privacy Notice text (last updated 2026-10-14) lives in one file, frontend/src/constants/terms.ts.
- App foundation added no native packages, so no rebuild of the dev build was needed.
- UI follows docs/prototype: all colors, fonts (Inter), spacing, radii and shadows live in frontend/src/constants/theme.ts; screens only compose shared components. Light theme only, as in the prototype.
- Prototype items left out on purpose: Google sign-in and the "Login as" picker (role switching is from the header).
- `users` create rule is an allowlist (fullName, contact, email, roles, fcmToken, createdAt) instead of only blocking verified and trustScore, so a client cannot fake isAdult or ratingCount.
