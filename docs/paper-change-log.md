# Paper Change Log (for Chapter 3 revisions and Chapters 4-5)
- Flutter -> React Native + Expo.
- On-device ID scan with auto pre-fill; ID data not stored in cloud.
- ML Kit photo auto-fill of editable item description.
- Panel suggestions: hide item until returned, 7-day deposit with open-ended rental, unique item attribute, one lender per match per item.
- Automatic verification replaces admin approval.
- Matching refinements (hard filters, fallback weights, generic label exclusion, ranking tiebreakers); weights described as initial heuristics, tunable.
- Chapter 4 AI metric: autofill acceptance rate (fields accepted vs edited) from autofillSuggested vs final values.
- Roles: the user chooses Lender, Borrower or Both at registration; the other role can be added later, never removed. Security rules require the lender role to list an item and the borrower role to post a request.
- Trust score is kept per role (lender trust score, borrower trust score), each starting at 3.00. A rating updates the role the rated person had in that rental. Same formula: (old x count + rating) / (count + 1). The two are never combined.
- Matching tiebreaker uses the item owner's lender trust score.
- Reviews: one overall 1 to 5 rating plus a comment. Per-category ratings (on-time, communication, item care, response) are future work.
- Messages: the inbox shows only the chats of the active role.
- ID verification is required for every user at registration and is fully automatic: the result is verified or rejected with a reason. There is no "flagged" outcome and no admin approval; admin handles only disputes and moderation. Rejection reasons: invalid details, under 18, name does not match the account (loose comparison), ID already registered, and a temporary lockout after more than 5 attempts in 24 hours that lifts by itself.
- ID step is an editable form (name, birthdate, ID type, ID number) that the ML Kit scan will pre-fill. Raw ID data is never uploaded or stored: the phone checks the details, the age (18+) and the name match itself, and sends the server only a SHA-256 hash of the normalized ID type and number plus the pass/fail results. The server applies a keyed HMAC (secret key) to that hash to detect an ID used on two accounts, applies the attempt limit, and stores only verified, isAdult, the verification time and the HMAC.
- Limitations to state: the pass/fail results come from the phone, so a tampered app could fake them (App Check is the planned safeguard); an unkeyed SHA-256 of an ID number could be reversed by guessing numbers, so it is sent only over HTTPS and never stored, while the stored value is the keyed HMAC.
- Trust scores have no stored starting value: a user with no ratings yet is shown 3.00 with 0 ratings, and only the rating function writes the fields.
- Not collected or stored: gender, address, avatar. Date of birth is used only for the age check and is not stored.
- Rentals are open-ended in every screen: start date only, and the deposit (daily rate x 7) replaces rental totals. The prototype's end dates and totals are not used.
- Prototype screens replaced: Verify / Review / Registration Submitted become ID form, check details, instant result. Dropped: "photo holding your ID", "Pending Admin Review", the 24-hour wording, Google sign-in, the "Login as" picker.
- Registration (2026-10-14): full name, email, contact number, password, confirm password, "Sign up as" (Borrower / Lender / Both), Terms checkbox, "Register your Account". "Continue with Google" is back on Register and Login (it was dropped on 2026-10-10); after Google sign-in a short "Complete your profile" screen asks for contact number, Sign up as and Terms.
- Email verification (free Firebase email link) after registering; the ID step stays blocked until the email is verified, and `verifyIdentity` also refuses unverified emails. Google accounts are already verified. A 6-digit email code is future work.
- ID step order: choose ID type, scan the ID (ML Kit text recognition), face check with motion (ML Kit face detection: blink or turn the head), editable form auto-filled from the scan (ID number, name, address, sex, birthdate), review, result (verified or rejected with reason), then back to Login. Manual entry remains the fallback when scanning fails.
- Privacy (Option B): all ID processing runs on the phone. Name, birthdate, address, sex, ID number and all images are never sent or stored. Only a SHA-256 hash of the normalized ID type and number plus pass/fail results reach the server. The face check moved earlier than first planned (it is part of the ID step now, not a later add-on).
- Terms and Conditions and Privacy Notice (2026-10-14) shown in the app and agreed to once at registration. It states what is and is not stored, that verification has no face matching, and refers to the Data Privacy Act of 2012 (RA 10173).
- Planned liveness check (not built yet): ML Kit Face Detection on the device, one or two random actions (blink, turn head). No images or face data are saved or uploaded; only pass/fail is sent. Limitation to state: liveness shows that a live person is present, not that they own the ID. There is still no face matching. Because the result comes from the phone, Firebase App Check (Play Integrity) is planned as a safeguard, to be decided when it is built.
